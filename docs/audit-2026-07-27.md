## 3. 🔴 ДЕФЕКТЫ — сломано прямо сейчас

### Д1. Окно чата раскрыто всегда и закрывает собой сайт

**Это ровно то, на что жаловался владелец.**

Что происходит: у окна чата стоит атрибут `hidden` — стандартный способ
спрятать элемент. Но работает он только тогда, когда наш собственный CSS не
задаёт элементу способ отображения. А он задаёт.

Доказательство — поиск по всему собранному CSS:

```
grep '\[hidden\]' dist/_astro/*.css   → НИЧЕГО НЕ НАЙДЕНО
```

При этом в том же файле:

```css
.chat-panel[data-astro-cid-pmyxn7tj]{ ... flex-direction:column;display:flex; ... }
@media (width<=640px){.chat-panel[...]{ ... position:fixed;inset:0}}
```

`display:flex` побеждает `hidden`. Результат: **на телефоне окно чата занимает
весь экран с момента загрузки любой страницы.** Сайта не видно.
На компьютере — коробка 380×560 постоянно висит в правом нижнем углу.

Хуже того, это окно **пустое**: приветствие добавляется в функции
`openChat()` (`ChatWidget.astro:331–335`), которая при загрузке не вызывается.
Гость видит пустую белую панель.

**Причина, а не симптом:** у Astro нет собственного сброса стилей, а в
`global.css` в слое `reset` правила для `[hidden]` не написано.

**Правильное решение** (код не пишу): добавить в `@layer reset` файла
`global.css` одну строку — `[hidden] { display: none !important }`.
`!important` обязателен: вес селектора `[hidden]` — 0-1-0, он проигрывает
`.chat-panel[data-astro-cid-…]` с весом 0-2-0.

Это устранение причины: правило починит `hidden` разом для всех элементов
сайта, а не только для чата.

### Д2. Каждая страница сообщает Google неверный собственный адрес

На всех 11 страницах тег canonical («вот мой настоящий адрес») противоречит
карте сайта и всем ссылкам:

| Что | Значение |
|---|---|
| canonical на странице | `https://santorinigid.com/tours.html` |
| карта сайта sitemap | `https://santorinigid.com/tours` |
| ссылки внутри сайта | `/tours` |
| разметка JSON-LD | `https://santorinigid.com/tours` |

Проверено выводом из `dist/`: все 11 canonical заканчиваются на `.html`,
все 10 адресов в `sitemap-0.xml` — без `.html`. Главная объявляет себя как
`/index.html`.

**Причина:** `astro.config.mjs:12` задаёт `build: { format: 'file' }`, из-за
чего `Astro.url.pathname` содержит `.html`, а `BaseLayout.astro:31` строит из
него canonical.

**Чем грозит.** Ради сохранения 14 лет SEO-истории адреса сохранили 1:1 с Wix.
Этот дефект бьёт ровно в эту цель: сайт сам говорит Google, что настоящие
адреса другие, чем те, что в карте сайта. Чинить **до** публикации — после
индексации исправлять дороже.

**⚠️ Ловушка при исправлении.** Простая замена «убрать `.html`» превратит
`/index.html` в `/index` — такой страницы нет. Главная должна получиться как
`https://santorinigid.com/` (или без косой черты — как в карте сайта, где
стоит `<loc>https://santorinigid.com</loc>`). Это надо предусмотреть отдельным
условием, иначе главная страница получит битый canonical.

### Д3. На 7 из 8 страниц с шапкой главная картинка грузится с задержкой

Это новая находка, в прошлом аудите её нет.

Картинка в шапке страницы — самый крупный элемент экрана. Google измеряет
скорость сайта по времени её появления (показатель LCP, Largest Contentful
Paint). Такой картинке нужно указывать «грузить сразу, в первую очередь».

Измерено точно: найдена первая картинка **внутри секции шапки** на каждой
странице собранного сайта.

| Страница | Как грузится |
|---|---|
| главная | `loading="eager" fetchpriority="high"` ✅ |
| экскурсии | `loading="lazy"` ❌ |
| контакты | `loading="lazy"` ❌ |
| о Санторини | `loading="lazy"` ❌ |
| VIP услуги | `loading="lazy"` ❌ |
| яхты | `loading="lazy"` ❌ |
| вертолёты | `loading="lazy"` ❌ |
| отели | `loading="lazy"` ❌ |
| обо мне, отзывы | шапки-картинки нет — пункт их не касается |

`lazy` означает «грузи потом, когда понадобится». Для картинки, которая видна
сразу при открытии страницы, это прямая потеря скорости: браузер сначала
разбирает страницу, потом обнаруживает картинку, и только тогда начинает её
качать.

**Причина:** компонент `Hero.astro:36–37` ставит приоритет по параметру
`priority`, но этот параметр передан только на главной
(`index.astro:99`). На остальных семи страницах с шапкой он не передан.

**Правильное решение:** картинка в шапке по определению видна сразу, поэтому
приоритет должен стоять по умолчанию, а не по просьбе. То есть значение
по умолчанию в `Hero.astro` надо поменять на «грузить сразу».

### Д4. Запасной вариант картинки на главной весит 534 КБ

Тоже новая находка.

В теге картинки на главной есть список вариантов под разные экраны (srcset) —
от 41 КБ до 330 КБ, всё правильно. Но у атрибута `src` (запасной вариант,
который берут старые браузеры и часть ботов) указан **файл, которого в этом
списке вообще нет**:

```
src="/_astro/hero-oia.C8YPuybw_1WOOJG.avif"   → 534 КБ, ширина 3000 пикселей
srcset: 640w(41 КБ), 960w(76 КБ), 1440w(144 КБ), 1920w(228 КБ), 2400w(330 КБ)
```

То есть при сборке создаётся и кладётся на сайт лишний файл в 534 КБ.
Это самая тяжёлая картинка сайта после мёртвого логотипа (см. Д5).

**Причина:** в `Hero.astro:34` список ширин задан как
`widths={[640, 960, 1440, 1920, 2400]}`, а исходный файл — 3000 пикселей
шириной. Astro делает запасной вариант из оригинала в полный размер.

**Важное уточнение, чтобы не было ложных ожиданий.** Все браузеры примерно
с 2016 года берут картинку из списка `srcset` и запасной вариант не качают.
То есть **на скорость сайта у живых гостей это не влияет** — это лишний вес
в репозитории и в каждой сборке, вопрос чистоты, а не быстродействия.

### Д5. Картинка на 1.1 МБ лежит на сайте, хотя нигде не используется

Файл `src/assets/img/logo-emblem.png` (1.1 МБ) **не упоминается ни в одном
файле проекта** — проверено поиском по всему `src/`. Но он всё равно попадает
в готовый сайт: `src/data/images.ts:11` затягивает в сборку **всю папку**
целиком через `import.meta.glob`.

Доказательство: `dist/_astro/logo-emblem.CKdzoZ11.png` — 1.1 МБ, самый
тяжёлый файл всего сайта. При этом ни одна страница на него не ссылается.

Он не замедляет открытие страниц (его никто не запрашивает), но занимает
место в репозитории и в каждой сборке.

**Правильное решение:** удалить файл. Если он нужен как запасной вариант
логотипа — перенести в папку вне `src/assets/img`, чтобы сборщик его не брал.

### Д6. Форма контактов не проверяет email и телефон

`src/pages/contacts.astro:190–202`: у формы стоит `novalidate` (отключена
встроенная проверка браузера), у полей стоит `required`, но в обработчике
проверяется **только имя**:

```js
if (!name) { ... return; }   // email и телефон не проверяются вообще
```

При пустом email заявка уйдёт в WhatsApp без обратного адреса.

Для сравнения, в форме отзыва это сделано правильно —
`ReviewForm.astro:227`: `if (!form.reportValidity()) return;`

**Правильное решение:** та же строка, что и в форме отзыва.

### Д7. Цвета сообщений в формах не читаются в тёмной теме

Новая находка. Цвета «успех» и «ошибка» вписаны в код напрямую, а не взяты
из палитры сайта, поэтому в тёмной теме они не меняются.

Расчёт контраста (норма 4.5:1):

| Цвет | Светлая тема | Тёмная тема |
|---|---|---|
| зелёный `#1a9e4b` («отправлено») | **3.48:1 — не проходит** | **4.15:1 — не проходит** |
| красный `#c0392b` («ошибка») | 5.44:1 — проходит | **2.66:1 — не проходит** |

Красный текст ошибки в тёмной теме даёт контраст 2.66:1 при норме 4.5:1 —
почти вдвое ниже. Человек с ослабленным зрением сообщение об ошибке не
прочитает.

Места: `ReviewForm.astro:521,525`, `contacts.astro:400,404`.

**Сюда же — четвёртый промах.** Звёздочка «поле обязательно» в форме отзыва
(`ReviewForm.astro:348–351`, цвет `--c-sunset-600` `#d95f28`) даёт на белом
фоне **3.74:1** — ниже нормы. Это единственный знак, которым отмечены
обязательные поля: если он плохо виден, человек не поймёт, что заполнять.

**Правильное решение:** завести в `global.css` токены (`--ok`, `--err`,
и более тёмный оттенок для звёздочки) с отдельными значениями для светлой и
тёмной темы — как уже сделано для всех остальных цветов сайта.

<a id="пробелы"></a>
## 4. 🟠 ПРОБЕЛЫ относительно стандарта середины 2026 года

Это не поломки — это то, чего профессиональный сайт в 2026 году обычно имеет,
а здесь нет.

### П1. Нет политики конфиденциальности — а сайт работает по законам ЕС

Отдельной страницы нет. При этом сайт собирает:

- имя, email, телефон (форма на `/contacts`);
- имя, контакт, до 3 фотографий (форма отзыва);
- IP-адрес каждого гостя уходит в Google — из-за шрифтов (см. П2).

Владелец ведёт деятельность в Греции — это Евросоюз, GDPR применяется
напрямую. Фраза «Ваши данные конфиденциальны» в форме
(`contacts.astro:177–180`) юридически политику не заменяет.

Это единственный пункт аудита с юридическими последствиями.

### П2. Шрифты грузятся с серверов Google — единственная внешняя зависимость

`BaseLayout.astro:107–120` подключает Inter и Playfair Display с
`fonts.googleapis.com`. Проверено по собранному HTML: это **единственный**
внешний домен, от которого зависит внешний вид сайта.

Это прямо противоречит главному принципу проекта — «что будет, если сервис
исчезнет». Ответ: сайт потеряет типографику. Плюс гости из России могут
получить задержку загрузки, а IP каждого гостя уходит в Google (пункт П1).

**Решение:** положить файлы шрифтов в проект (папка `public/fonts/`). Тогда
внешних зависимостей становится ровно ноль, и утечка IP исчезает.

### П3. На сайте нет никакой статистики посещений

Ни Google Analytics, ни Яндекс.Метрики, ни лёгких альтернатив (Plausible,
Umami, Cloudflare Web Analytics). Проверено поиском по `src/` и `dist/`.

Для сайта, который приводит клиентов, это существенно: непонятно, сколько
человек заходит, с каких страниц уходят, какие запросы приводят гостей.
Без этого продвижение (`docs/promotion-plan.md`) идёт вслепую.

Рекомендую вариант без кук и без баннера согласия — тогда и GDPR не
усложняется. Это отдельное решение владельца.

### П4. Заявка на PWA не завершена

CLAUDE.md фиксирует вопрос «нужен ли режим приложения (PWA)». Ответа нет,
но половина работы уже сделана: `public/site.webmanifest` есть и подключён
на всех страницах.

Однако как PWA он не работает:
- нет service worker (проверено — файлов нет, регистрации в коде нет);
- в манифесте только 2 иконки, обе не подходят под требование
  «512×512 с purpose: maskable» — без неё Android не предложит
  «установить приложение».

Сейчас это «манифест ради манифеста». Либо доделать (тогда сайт можно
установить на телефон и он откроется без интернета), либо оставить как есть
и не считать сайт приложением.

### П5. Что можно и чего нельзя по защите на GitHub Pages — честно

GitHub Pages — простая раздача файлов. Он **не позволяет** задавать
HTTP-заголовки: ни `Content-Security-Policy`, ни `X-Frame-Options`, ни
`Strict-Transport-Security`. Никакой файл конфигурации это не изменит.

Что **доступно**: тег `<meta http-equiv="Content-Security-Policy">` в
`<head>`. Проверено — сейчас его нет (0 тегов `http-equiv` в собранном HTML).

Для статического сайта без входа в личный кабинет риск невысокий. Но при
подключении ИИ-чата (см. Б4) meta-CSP станет реальной защитой.

Важно: не стоит обещать владельцу заголовки, которых этот хостинг дать не может.

### П6. Нет README — лица проекта на GitHub

Файла `README.md` в репозитории нет. Это первое, что видит любой, кто
откроет страницу проекта на GitHub, — сейчас там будет пусто.
Документация для владельца есть (`ПРОЧТИ-МЕНЯ.md`), но GitHub показывает
именно `README.md`.

### П7. Тёмная тема написана, но включить её нельзя

`global.css:221–234` полностью описывает тёмную тему для
`:root[data-theme='dark']`, но **ни одна кнопка на сайте этот атрибут не
ставит** — проверено поиском по всему `src/`.

Работает только автоматический режим (`prefers-color-scheme`, строки 204–219)
— по настройке телефона. Гость не может переключить тему вручную.

Либо добавить переключатель, либо убрать неиспользуемую половину правил.
Сейчас это код, который никогда не выполняется.

### В1. ⚠️ Адрес `/vip-service` — проверить на первом же деплое

Сайт собирается в отдельные файлы: `tours.html`, `contacts.html` и так далее.

dist/vip-service.html          ← страница «VIP услуги»

    helicopter-tours.html

Когда придёт запрос на `/vip-service`, серверу надо выбрать: отдать файл

браузере адрес вида `https://2026glai.github.io/santorinigid/vip-service`.

сборки (`format: 'directory'`), тогда получатся папки с `index.html` внутри,
и такой неоднозначности не будет.
